Case file 01In daily use since 2026

Knowledge Base Platform with Built-in LLM

A containerised web application that serves the documentation produced in the application discovery programme and makes it conversationally searchable. It runs as a Flask application in Docker on Snowpark Container Services with a JavaScript front end, and layers a Snowflake Cortex agent over two Cortex Search services, so engineers and non-technical staff can ask questions in plain language and receive answers that cite their sources. It worked from first launch and is used daily by about 10 support and development staff, with no user-reported issues since.

My role
Sole developer, solution designer, deployer and maintainer
Build type
New build: documentation platform with agentic retrieval
Business value
Turns static documentation into a cited knowledge source and reduces key-person risk
Relevant to
Applied AI, AI automation, platform, technical documentation and internal tools roles

What I delivered

  • Knowledge extraction with AI. Claude Code with MCP tooling pulled source code, stored procedures and business logic out of 23 legacy applications. That became versioned documentation and a business rules catalogue, with every finding checked against the source.
  • Container platform. Flask API and viewer packaged in Docker on Snowpark Container Services, with a multi-stage build that bundles a Svelte and TypeScript architecture viewer.
  • Agentic retrieval. A Cortex agent orchestrates two Cortex Search services, one over document chunks and one over SQL object definitions, and returns cited answers with section-level source trails. Cortex COMPLETE is the fallback.
  • Deterministic routing for roster-style questions, such as listing every SQL Agent job, where top-k retrieval is the wrong tool. The reasoning is documented in code.
  • Git-driven content. The app reads documentation straight from the repository branch in Snowflake, so it always serves what version control holds.
  • Retrieval-only grounding. Every answer is grounded by Cortex Search at question time. No facts are precomputed into prompts, and prompts are assembled server side only; the browser never sends a system prompt.
  • A deliberate platform decision. I built, then reverted, a direct LLM API path in favour of Cortex. Cortex needs no API key, egress rule or key rotation, authenticates with the container's own session and still offers Claude models.
  • Operational hardening. Request time budgeting with fallback paths, usage logging, chat history and feedback capture, cache-busting build IDs and refresh endpoints.
  • Delivery pace. Redeployed 137 times through the CI/CD pipeline in its first five weeks.
  • Features people use. Pinned documents, chat scoped to selected documents, a full document tree, printing and Mermaid diagrams.
  • Security and reliability review of the live app, with each finding fixed on its own branch through a reviewed pull request.
  • Measured documentation quality. Companion documentation standards define the structure the app parses. An audit found 221 of 1,092 business rules unreadable by the assistant, and version 2.0 of the standard closed that gap.

What it demonstrates

  • End-to-end agentic application delivery: container platform, retrieval design, prompt and orchestration discipline and UI, beyond simple API calls.
  • Documentation treated as a product: standards authorship, a docs-as-code pipeline and measurable quality feedback loops.
  • AI applied to a real operational problem with governance, logging and fallback behaviour, consistent with responsible production use.
Case file 02 | Own productPilot | Docker test server

Reqentra SaaS Helpdesk and Safe Space

Reqentra is my own product, currently in pilot: a multi-tenant SaaS helpdesk built in Next.js and TypeScript and deployed as Docker containers. Self-service signup provisions an isolated tenant per customer on its own subdomain with TLS. Agents sign in through their company's own directory, and Microsoft 365 mailboxes connect over Microsoft Graph. The source is in GitHub and the app is hosted on a Docker test server. Safe Space is its AI feature: before an agent's reply reaches a customer, a self-hosted language model judges whether it is unprofessional, and incoming requester messages are checked for passive aggression. A reply copilot on the same model drafts, improves and summarises. Built September to October 2026.

My role
Founder, sole developer and operator
Build type
New product: multi-tenant SaaS with a self-hosted LLM feature
Business value
Protects tone with customers without sending ticket text to an external AI service, with an auditable record
Relevant to
Applied AI, SaaS and product engineering, platform and AI automation roles

What I delivered

  • Physical tenant isolation. A provisioner service creates an isolated tenant per customer, with its own container, its own database and its own subdomain with TLS, instead of a tenant key in a shared database. A separate public front door handles enrolment.
  • Enterprise identity and mail. Single sign-on through Microsoft Entra ID, Google and generic OIDC, passkeys for the administrator account, and Microsoft 365 mailboxes connected over Microsoft Graph with OAuth consent.
  • Backups the customer owns. Continuous replication with point-in-time recovery to S3-compatible object storage in the customer's own cloud account, in a region they choose and under keys they can revoke, proven by a scripted restore drill.
  • Self-hosted by design. An open-weight model (Qwen 2.5 7B Instruct) served by Ollama on infrastructure the operator controls, so ticket text never goes to a third-party API. Two switches, operator and customer, must both be on before any text leaves the tenant container.
  • Two checks for the two sides of a ticket. Agent replies are judged for unprofessional tone (passive-aggressive, curt, dismissive, lecturing, sarcastic or blaming) as an answer to the requester's last message. Requester messages are checked only for passive aggression, because a customer is allowed to be blunt.
  • Prompt evaluation on held-out examples. The first, narrower prompt let three plainly unprofessional replies through. The revised prompt, with context and worked examples, judged 9 of 9 unseen replies and 7 of 7 test messages correctly, at 4 to 9 seconds per check on CPU.
  • Human in the loop. A flagged reply is held back with the reason, the quoted words and a one-click rewrite. An agent may still send it, and that is recorded in an admin audit log that is never deleted. Copilot output only ever appears as a preview, so any prompt injection hidden in ticket text cannot act on its own.
  • Graceful degradation. A configurable phrase list judges whenever the model is off, unreachable, slow or returns an unreadable answer, so replies never stop.
  • Inference without a GPU. Verdicts cached under a hash so no ticket text is stored, one fixed context size to avoid model reloads, and a priority queue that serves agents before background scans.
  • Governance. Turning Safe Space on is a logged business decision by an administrator or helpdesk lead, and every agent agrees to it before using the app.
  • Engineering workflow. Every change on its own branch through a pull request; developed on Windows, built and run under WSL, then deployed to the Docker test server.

What it demonstrates

  • SaaS platform design: tenant isolation, enterprise single sign-on, mail integration and backups the customer owns.
  • End-to-end applied AI product work: model choice, prompt design, evaluation, latency, fallback and user experience.
  • Data-sovereign AI: useful LLM features delivered without sending customer data to a third party.
  • AI governance designed into the product: consent switches, human review, audit trail and explicit agreement.

Case file 05Proof of concept, no end users

Warehouse Picking App

A proof of concept: a Snowflake-native rebuild of a legacy warehouse order-picking application. It shows how a desktop-style process could move to a web-based tool backed by Snowflake and on-prem SQL Server data. It was rebuilt from the legacy application, without end users involved.

My role
Sole developer and solution designer
Build type
Proof of concept: rebuild of a legacy operational application
Business value
Input for a modernisation decision: web access, traceability and supportability on Snowflake
Relevant to
Application development, platform, DevOps, data automation and internal tools roles

What I delivered

  • Streamlit operational app with a picking grid, cart and picking workflow, bulk operations and printable pick-list reports.
  • A reusable, manifest-driven sync engine: table syncs are configured in YAML instead of hard-coded scripts.
  • An Azure DevOps pipeline designed to run every 15 minutes during operational hours on a self-hosted agent with on-prem SQL Server access.
  • MERGE and watermark patterns for near-real-time SQL Server to Snowflake synchronisation.
  • Parallel execution with ThreadPoolExecutor, retry logic and pipeline run logging.
  • Parameterised stored procedures for transactional operations, to reduce SQL injection risk.
  • Printable HTML reports stored in Snowflake for audit and reprint support.

What it demonstrates

  • How a legacy desktop application can be reverse engineered and rebuilt as web-based tooling on a modern data platform.
  • Hybrid integration thinking: on-prem SQL Server, an Azure DevOps agent, Snowflake, a Streamlit UI and audit tables.
  • Supportability and security-minded design in a proof of concept: parameterised procedures, audit tables and run logging.
